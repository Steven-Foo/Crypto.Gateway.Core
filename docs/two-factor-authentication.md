# Two-factor authentication — design

> **Status: BUILT AND VERIFIED end to end (2026-09-24); extended with a per-account force/optional switch
> (2026-09-25, §4.1).** All nine steps in §11 are done: solution builds clean, both hosts exercised over
> HTTP (58 checks on Ops, 29 on the merchant portal) with authenticator codes generated by an independent
> RFC 6238 implementation, and both db/sql scripts applied twice to fresh databases. Frontend contracts are in
> `backoffice-frontend-integration.md` §3b/§3c and `merchant-portal-frontend-integration.md` §3b. T3 throughout: it changes the `identity` and `merchantidentity` schemas and the
> authentication boundary (CLAUDE.md §6). Decisions in §0 were approved before any code was written.

Authenticator: **TOTP (RFC 6238)** — Google Authenticator, and equally Authy / 1Password / Microsoft
Authenticator, which all read the same QR. Scanned once at enrollment; the app derives a new 6-digit code
every 30 seconds offline from then on.

## 0. Decisions taken (user, 2026-09-21)

| Decision | Consequence |
| --- | --- |
| **Every staff and every merchant-portal user enrolls.** | Enrollment is *forced*, not offered (§4). No unenrolled account can exist, so the login form can always show the code box. |
| **A code is prompted per ACTION, not per time window.** | Every performance of a guarded action prompts for a code — `X-2FA-Code` header on each request. No grant, no window. |
| **No single-use/replay guard on the code.** | A valid code is accepted for as long as it is valid (its step ±1). A wrong code refuses that action and changes nothing; the operator simply retries. See §6.1. |
| **Merchant portal: login 2FA only, no guarded actions yet.** | `MerchantIdentity` gets the enrollment + login half. No policy table, no action catalog on that side (§9). |
| **TOTP hand-rolled** (RFC 6238 over BCL `HMACSHA1`), no new package. | Provable against the RFC's published test vectors; no supply-chain surface added on the auth path (§11). |
| **`AesGcmSecretBox` promoted to SharedKernel.** | One AES-GCM implementation; `Merchant.ISecretCipher` becomes a thin adapter, each identity module gets its own (§7). |

Two things follow from "everyone enrolls" that simplify the earlier draft, and one that costs something:

- **No half-authenticated login state.** The previous draft split login into password → challenge → code,
  because the server could not know whether to ask for a code. With universal enrollment it always asks, so
  login stays **one call** carrying username + password + code. That deletes an entire table
  (`StaffTwoFactorChallenge`), four endpoints, and the whole class of "a challenge token got treated as a
  session" bugs. *Alternative:* keep the two-leg flow — better UX on a mistyped code (no password re-entry)
  and cleaner separate error codes. *Trade-off taken:* a mistyped code means retyping the password, which
  password managers autofill anyway; worth it to remove a half-authenticated state from an auth boundary.
- **No enrollment-coverage warning** on the settings screen, and `two_factor_not_enrolled` becomes
  unreachable in normal operation (kept as a fail-closed backstop, §6).
- **Bulk work is unconstrained.** With no replay guard, a run of approvals proceeds at typing speed (§6.1).

Scope of this phase: `Platform/Identity` + `Api/OperationsApi` (login + guarded actions), and
`Platform/MerchantIdentity` + `Api/MerchantPortalApi` (login only).

**Ledger impact: NONE.** 2FA decides whether an action is permitted; it never changes what is posted.
**Key impact: NONE in the §10 sense** — a TOTP secret is an authentication secret, not a signing key. It is
still encrypted at rest (§7).

## 1. The flows

```
STAFF LOGIN
  POST /ops/auth/login { username, password, code }  ──▶  session (cookie + CSRF, exactly as today)
  not yet enrolled ──▶ session restricted to the enrollment endpoints only (§4)

ADMIN PICKS WHAT IS GUARDED
  Settings ▸ Guarded actions ──▶ tick "Record hot-wallet top-up"  ──▶ platform-wide, immediate

ANY ADMIN PERFORMS IT
  POST /ops/treasury/top-up                       ──▶ 403 ops.two_factor_required { action }
  POST /ops/treasury/top-up  X-2FA-Code: 418392   ──▶ 200

MERCHANT PORTAL (this phase)
  POST /portal/auth/login { username, password, code }  ──▶  session
  no guarded actions — nothing else changes
```

## 2. Where it lives, and why

| Concern | Home | Why |
| --- | --- | --- |
| TOTP secret, recovery codes, verification | `Platform/Identity` and, independently, `Platform/MerchantIdentity` | Each owns *who you are and how you prove it*. The two identity modules stay independent (§4.5) — they share only SharedKernel primitives, exactly as they already share `Pbkdf2PasswordHash` and `OpaqueToken`. |
| TOTP algorithm, AES-GCM secret box | SharedKernel primitive + a port per module | §4.4 — Domain/Application never touch crypto primitives directly. One implementation, two thin adapters (§7). |
| **The catalog of guardable actions** | **`Api/OperationsApi/Security/GuardedActions.cs` (the HOST)** | Same precedent as `OpsPermissions`: the codes name capabilities across Treasury/Withdrawal/Merchant/Compliance, and **Identity must not know those modules exist** (§4.5). Identity stores and matches opaque strings. |
| The stored policy (which actions are guarded) | `Platform/Identity` | A property of the identity system, not of Treasury. Host supplies the vocabulary; Identity stores the selection. |
| The enforcement filter | Host (`RequireTwoFactor`) | Where `RequirePermission` already lives — the host is where a route meets a policy. The *decision* is Identity's. |

## 3. Domain model

### 3.1 `StaffTwoFactor` — its own table, not columns on `StaffUser`

```
identity.StaffTwoFactor
  Id                   uniqueidentifier  PK
  StaffUserId          uniqueidentifier  UNIQUE — one factor per account, enforced at the DB
  SecretCiphertext     varchar(512)      AES-256-GCM blob, base64 (version+nonce+tag+ciphertext)
  Status               varchar(16)       Pending | Active | Disabled
  EnrolledAt           datetimeoffset    null until confirmed
  FailedAttempts       int               consecutive failures; reset to 0 on any success
  LockedUntil          datetimeoffset    null
  rowversion
```

**Decision: a separate table rather than three columns on `StaffUser`.**
*Reason:* `StaffUser` is loaded on every login and every account-admin read. Columns on it mean the secret is
materialised on paths with no business holding it, and one careless projection leaks it into a response. A
separate table makes "load the secret" an explicit act.
*Alternative:* columns on `StaffUser` (no join). *Trade-off:* one extra PK lookup, on the 2FA paths only.
*Future:* the identical shape is what `MerchantIdentity` gets (§9).

`Status = Pending` is the state between "secret generated, QR displayed" and "first code verified". A pending
enrollment **grants nothing** — it satisfies neither login nor a guarded action. Without it, an interrupted
enrollment leaves an account that believes it has 2FA and an operator who cannot produce a code.

### 3.2 `StaffRecoveryCode`

```
identity.StaffRecoveryCode
  Id, StaffUserId, CodeHash (PBKDF2, reusing SharedKernel.Pbkdf2PasswordHash), UsedAt, CreatedAt
```

Ten codes issued at enrollment, displayed **once**, stored hashed like a password, single-use. Accepted in
the same `code` field at login.

**A recovery code satisfies login. It does NOT satisfy a guarded action.**
*Reason:* recovery codes exist so a lost phone does not lock someone out of the back office. They are not a
factor a person deliberately carries at the moment they move money — if one clears a guarded action, the
whole control degrades to "whoever has the printout". Someone who has lost their authenticator logs in with
a recovery code and their first guarded action is re-enrolling.

### 3.3 `TwoFactorPolicyVersion` — append-only, config-floored

```
identity.TwoFactorPolicyVersion
  Id, Seq (clustered identity)
  GuardedActionsCsv    varchar(4000)     opaque strings, pipe-joined — the hosts vocabulary
  UpdatedBy            nvarchar(128)     from the validated session, never the body
  Note                 nvarchar(512)     null
  UpdatedAt            datetimeoffset
```

Deliberately the **same shape as `compliance.ScreeningPolicyVersion`**, for the same three reasons, which
transfer exactly:

- **Append-only.** An action performed last month must stay explainable against the policy in force then. A
  mutable settings row destroys that. `GET .../policy/history` reads the trail.
- **Config is the floor, a stored version overrides.** `Identity:TwoFactor:GuardedActions` seeds the
  effective policy so a fresh environment boots with a defined posture; the first save takes over and
  `source` reads `Stored`. Config alone means every change is a deployment; DB alone means a new environment
  boots with the control undefined.
- **`source: Configuration | Stored`** distinguishes "nobody has set this" from "someone set it to exactly
  the default". Only one of those is a question worth asking.

`RequireAtLogin` and `StepUpWindowSeconds` from the earlier draft are **gone**: login 2FA is now
unconditional, and there is no window.

Cache: a singleton `TwoFactorPolicyCache` (~30s) behind a scoped `TwoFactorPolicyProvider`, invalidated
immediately on the host that saved — copied from `ScreeningPolicyProvider`/`ScreeningPolicyCache`, which
already solved this.

### 3.4 One added column

`StaffSession.TwoFactorMethod` (`varchar(16)` null) — `Totp` or `RecoveryCode`, recorded at login. It is
what lets a guarded action refuse a session that only ever proved itself with a recovery code (§3.2), and it
is useful in the audit trail. Additive and nullable, so existing sessions stay valid through the migration.

## 4. Forced enrollment

"Everyone enrolls" is only true if it is enforced, so it is a state, not a policy anyone remembers.

`MerchantIdentity` already has the precedent — `MustChangePassword`. Same mechanic, and no new column is
needed because the state is derivable: **no `StaffTwoFactor` row with `Status = Active` ⇒ not enrolled.**

- Login with correct credentials and no active factor **succeeds**, and the `code` field is ignored.
- The session it issues is **restricted**: `StaffBearerAuthMiddleware` lets it reach only
  `/auth/2fa/enroll`, `/auth/2fa/enroll/confirm`, `/auth/2fa/status`, `/auth/me` and `/auth/logout`.
  Everything else → **403 `ops.two_factor_enrollment_required`**.
- `/auth/me` and the login response carry `twoFactorEnrolled: false`, so the SPA routes straight to the QR
  screen instead of discovering the restriction one failed call at a time.
- Confirming enrollment **upgrades the current session in place** (no re-login), so the flow is: sign in →
  scan → enter code → land on the dashboard.

That makes a brand-new account's first act enrollment, and makes "an unenrolled account" a state that cannot
persist past first login.

### 4.1 The live force/optional switch — `RequireTwoFactor` (2026-09-25)

**Decision (user, 2026-09-25): 2FA is forced by DEFAULT, but an admin can flip a per-account switch to make
it optional, independently of whatever that account has actually bound.** "Force at creation, force/optional
after creation, on both staff and merchant-portal accounts, including the merchant's own primary account" —
confirmed with the user's PM before building.

This is a **second, independent axis** from everything in §3–§4 above: bind status (`StaffTwoFactor.Status` /
`MerchantUserTwoFactor.Status` — Pending/Active/Disabled, "has this account got a factor") is untouched by it.
The new axis is just "does this account currently have to prove one". The two combine into exactly four
cases, and this is the contract every caller must satisfy:

| Switch | Bound? | Login | Guarded actions (Ops only) |
| --- | --- | --- | --- |
| **Off** | No | No code asked. `twoFactorEnrolled: true` — nothing to finish. | None demand a code. |
| **On** | No | Forced enrollment (§4) — restricted session until the QR is scanned. | N/A until enrolled. |
| **Off** | **Yes** | **Still no code asked** — the existing binding is not touched or destroyed, just ignored while the switch is off. | None demand a code — same as never-bound. |
| **On** | Yes | Code required, exactly as before this switch existed. | Demand a code, exactly as before. |

**Where it lives:** `StaffUser.RequireTwoFactor` / `MerchantUser.RequireTwoFactor` (bool, set at creation,
flippable after) is snapshotted onto the session at login — `StaffSession.RequireTwoFactor` /
`MerchantUserSession.RequireTwoFactor` — same principle as the role/permission snapshot (§3.3-adjacent): a
switch flipped mid-session takes effect at that account's NEXT login, not retroactively. Two formulas on the
session carry the whole behaviour:

```
TwoFactorEnrolled   = !RequireTwoFactor || TwoFactorMethod is not null
AuthenticatorProven = !RequireTwoFactor || TwoFactorMethod == Totp
```

A switch-off session reads both as satisfied unconditionally, which is what lets it skip 2FA everywhere —
at login (no restricted session, §4 never triggers) and, on the Ops side, on every guarded action (§6's
filter checks `principal.RequireTwoFactor` immediately after `policy.IsGuarded(action)`; off ⇒ pass through
without ever asking for a header). Critically, `TwoFactorMethod` itself stays an **honest record of what was
actually proved** — a switch-off login records `null`, never a fabricated `Totp`, even when the account has a
real active factor sitting unused. Flipping the switch back on demands a code again immediately, with no
re-enrollment, because the bound secret was never disturbed.

**The escalation risk, and how it's closed:** a switch-off account bypasses 2FA on literally everything for
that account, by design (the table above). So the write path that flips someone's own switch off must not be
self-service, or a compromised admin session could clear its own requirement and quietly zero every guarded
action's protection with no further code ever needed. Closed the same way `SetStatusAsync` already refuses
self-disable: `StaffAccountService.SetRequireTwoFactorAsync` / `MerchantAccountService.SetRequireTwoFactorAsync`
take the caller's own id and refuse a self-target (`staff_user.cannot_change_own_two_factor_requirement` /
`merchant_user.cannot_change_own_two_factor_requirement`) — another admin must do it. No change was needed to
the always-guarded self-protection invariant in §5.1: the toggle endpoints sit behind the existing
`ops.accounts.manage` / `portal.accounts.manage` permission and, on the Ops side, `.RequireTwoFactor(GuardedActions.AccountsManage)`
like every other account-admin write.

**HTTP surface, both hosts:**

```
POST /api/v1/ops/accounts            { username, roleId, requireTwoFactor? }  → requireTwoFactor defaults TRUE
PATCH /api/v1/ops/accounts/{id}/two-factor  { requireTwoFactor }               → ops.accounts.manage + X-2FA-Code

POST /api/v1/portal/accounts         { username, displayName?, roleId?, requireTwoFactor? }  → defaults TRUE
PATCH /api/v1/portal/accounts/{id}/two-factor  { requireTwoFactor }            → portal.accounts.manage

POST /api/v1/ops/merchants           { ..., portalAccountRequireTwoFactor? }   → defaults TRUE
                                       (the merchant's auto-provisioned FIRST/primary portal account —
                                        the primary account is exempt from disable, never from this switch)
```

Every create-account/create-merchant field **defaults to `true`** — an older client that omits it gets
today's forced behaviour, never a silently-unprotected account. Every account view (`StaffAccountView` /
`MerchantAccountView`) now carries `requireTwoFactor` so a settings screen can render current state without a
second call. **Migration note:** existing rows were backfilled `true` on the `AddStaffRequireTwoFactor` /
`AddMerchantUserRequireTwoFactor` migrations — every account and every already-live session keeps demanding
exactly what it demanded before this feature shipped, until an admin explicitly turns a switch off.

## 5. The guarded-action catalog (the expandable part)

```csharp
// Api/OperationsApi/Security/GuardedActions.cs — owned by the host, like OpsPermissions.
public static class GuardedActions
{
    public const string TreasuryTopUp            = "ops.treasury.top-up";
    public const string TreasuryColdWallet       = "ops.treasury.cold-wallet";
    public const string WithdrawalApprove        = "ops.withdrawals.approve";
    public const string WithdrawalSettlement     = "ops.withdrawals.record-settlement";
    public const string BalanceAdjust            = "ops.balances.adjust";
    public const string MerchantSettlementWallet = "ops.merchants.settlement-wallet";
    public const string SweepSettings            = "ops.sweep.settings";
    public const string AccountsManage           = "ops.accounts.manage";
    public const string RolesManage              = "ops.roles.manage";
    public const string CompliancePolicy         = "ops.compliance.policy";

    /// Always guarded. Not in `Guardable` — it can never be switched off (§5.1).
    public const string TwoFactorPolicy          = "ops.security.two-factor-policy";

    public static IReadOnlyList<GuardableAction> Guardable { get; } = [ /* code + display label + group */ ];
}
```

**Adding an action later is three lines:** a `const`, an entry in `Guardable`, and
`.RequireTwoFactor(GuardedActions.X)` on the route. It then appears in `GET /ops/two-factor/actions`, which
is what the settings screen renders — so the UI picks it up with no frontend change. Nothing in Identity
changes, because Identity only ever compares strings.

An action code is **not** a permission code, even where the strings coincide. A permission asks *may this
role do it at all*; a guarded action asks *must this person prove themselves again right now*. Kept separate
so an action can be guarded without inventing a permission, and a permission can be split without disturbing
the policy. Applied in that order on the route:

```csharp
app.MapPost("/api/v1/ops/treasury/top-up", RecordTopUpAsync)
   .RequirePermission(OpsPermissions.Treasury.Manage)
   .RequireTwoFactor(GuardedActions.TreasuryTopUp);
```

**Permission first, 2FA second** — no point demanding a code for something the caller may not do, and doing
so confirms the action exists to someone with no access to it.

### 5.1 The self-protection invariant

**`ops.security.two-factor-policy` is permanently guarded and cannot be removed from the guarded list.**

Without it the control unlocks itself: an attacker on a stolen admin session opens the settings screen,
unticks every action, and every code prompt is gone. Hardcoding it means weakening 2FA always costs a fresh
code from a real authenticator. Same reasoning that makes the shipped `AlwaysBlockIndicators` add-only in the
screening policy: the rule that must never come off in a web form is the one protecting the rest.

Two consequences, both required:

1. **Resetting another user's 2FA is a guarded action and is audited.** Account recovery is the standard
   bypass — if an admin can clear a colleague's enrollment without a code, that is the way through. It sits
   under `AccountsManage`.
2. Enrollment endpoints are **not** guarded (they are authenticated and self-scoped), or a platform with
   nobody yet enrolled could never enroll anyone.

## 6. Enforcement — one code per performance of a guarded action

```
RequireTwoFactor(action):
    principal = validated session                 (middleware already ran)
    policy    = TwoFactorPolicyProvider.Current() (cached ~30s)

    if action not in policy.GuardedActions and action != TwoFactorPolicy
        → pass through

    if caller has no Active StaffTwoFactor
        → 403 ops.two_factor_not_enrolled          (backstop; unreachable under §4)

    if session.TwoFactorMethod == RecoveryCode
        → 403 ops.two_factor_recovery_not_accepted (§3.2)

    code = request header X-2FA-Code
    if absent
        → 403 ops.two_factor_required { action }
    if locked out
        → 403 ops.two_factor_locked
    if the code does not verify against the secret (this step, ±1)
        → 401 ops.two_factor_invalid_code   ← the action does NOT run; nothing is mutated

    → pass through
```

The filter runs **before the handler**, so a refused code means the action never happened — no partial
write, nothing to undo. The operator clicks again, the modal reopens, they type a code, it goes through.

The code rides in the **`X-2FA-Code` header**, not the body — so no request model anywhere changes, and one
frontend interceptor covers every guarded action ever added: catch `ops.two_factor_required`, prompt, replay
the original request with the header.

### 6.1 No replay guard — retry is free, and a code stays usable while it is valid

**Decision (user, 2026-09-23): the code is verified, not consumed.** There is no single-use tracking. A
valid code works for as long as TOTP says it is valid (its own 30-second step, ±1 for clock skew), so a run
of guarded actions proceeds at typing speed rather than at one per step. A wrong code refuses that one
action, mutates nothing, and the operator retries straight away.

*Reason:* the alternative — consuming each code — caps a staff member at one guarded action per 30 seconds,
because the authenticator has no second code to give inside a step. Forty settlement approvals would be
twenty minutes of watching a phone, which is how a control stops being used as designed.

*Residual risk, stated plainly:* a code observed by someone else (shoulder-surfed, screenshotted, captured
from a log or a proxy) is usable for up to ~90 seconds. It is **not** a credential on its own — the holder
also needs a live session on that account, which means the cookie or bearer token, the CSRF token, and the
permission. So this widens an existing session-compromise window slightly; it does not create a new path in.

*Two things that follow, and both are required rather than optional:*

1. **The `X-2FA-Code` header must never be logged.** With no replay guard, a code sitting in a request log
   is usable by whoever reads that log inside the window. It is added to Serilog's request-logging
   redaction list alongside `Authorization` and `Cookie`, and the same applies to any reverse-proxy access
   log in front of the host (`docs/ec2-staging.md`).
2. **Skew stays at ±1 step and is not widened.** Every extra step both lengthens that window and enlarges
   the space a brute-forcer covers per guess.

**Lockout is tuned for retry, not against it** (§7): the threshold is deliberately generous, because a
mistyped or just-expired code is the normal case here and a control that locks people out on ordinary typos
gets routed around.

## 7. Secret handling

- Secret: 160-bit CSPRNG, Base32, provisioning URI
  `otpauth://totp/CryptoPaymentEngine:{username}?secret=...&issuer=CryptoPaymentEngine&digits=6&period=30`
  — the exact format Google Authenticator's scanner expects. Returned with a QR payload.
- **At rest: AES-256-GCM.** Not plaintext, not a hash (verification needs the secret back).
- **Never logged; never returned after enrollment.** The provisioning URI is returned exactly once, from the
  enroll call, over the authenticated session. There is no "show me my secret again" endpoint — losing it
  means re-enrolling, which is the correct cost.
- Verification window: ±1 step (±30s) for clock skew. Not wider — each extra step multiplies the guess space
  a brute-forcer gets per attempt.
- **Never logged**, in any form — including the `X-2FA-Code` request header (§6.1) and the login body.
- Lockout: **10 consecutive failures → 15-minute lock** on the factor, audited; any success resets the
  counter. Deliberately generous, because retry is the designed behaviour (§6.1) and a mistyped or
  just-rolled code is the normal case — but not absent: six digits is 10⁶, and an unthrottled endpoint that
  accepts a guess per request is brute-forceable by a caller who already holds a session.

**Approved refactor.** `AesGcmSecretCipher` exists in `Merchant/Infrastructure/Security`, and neither
identity module may reference it (§4.5). The algorithm is promoted to **`SharedKernel.AesGcmSecretBox`** — a
pure primitive, exactly like the existing `Pbkdf2PasswordHash` and `OpaqueToken` that both identity modules
already share. `Merchant.ISecretCipher` becomes a thin adapter over it (behaviour byte-identical, covered by
Merchant's existing tests), and each identity module gets its own port and adapter. One AES-GCM
implementation is one place to review; the rejected alternative was three copies of a security primitive
that must not drift.

Cipher key: `Identity:TwoFactor:EncryptionKey` / `MerchantIdentity:TwoFactor:EncryptionKey` in config (same
posture as the merchant cipher key today), KMS-wrappable later at the same seam.

## 8. HTTP surface — Ops

All under `/api/v1/ops`. Envelope and `errorCode` discipline per `backoffice-frontend-integration.md` §2.

| Method | Route | Gate | Purpose |
| --- | --- | --- | --- |
| POST | `/auth/login` | — | Body gains `code`. Response gains `twoFactorEnrolled`. |
| POST | `/auth/2fa/enroll` | session | Generates a Pending secret; returns provisioning URI + QR **once**. |
| POST | `/auth/2fa/enroll/confirm` | session | First code → Active; returns the 10 recovery codes **once**; upgrades the current session. |
| GET | `/auth/2fa/status` | session | `{ enrolled, status, enrolledAt, recoveryCodesRemaining }`. |
| POST | `/auth/2fa/recovery-codes` | session + **X-2FA-Code** | Regenerate; invalidates the old set. |
| POST | `/accounts/{id}/2fa/reset` | `ops.accounts.manage` + **X-2FA-Code** | Admin clears a colleague's enrollment. Audited. That user is unenrolled at next login (§4). |
| GET | `/two-factor/actions` | `ops.roles.view` | The catalog the settings screen renders. |
| GET | `/two-factor/policy` | `ops.roles.view` | `{ current, configuredDefaults, source }`. |
| PUT | `/two-factor/policy` | `ops.roles.manage` + **X-2FA-Code (always)** | Save a new version. |
| GET | `/two-factor/policy/history` | `ops.roles.view` | The append-only trail. |

There is **no** self-service `DELETE /auth/2fa` — 2FA is mandatory (§0), so disabling one's own factor is not
an available operation. Losing a device is handled by a recovery code, or by an admin reset.

New codes for `OpsErrorCodes` (published contract — renaming one is a breaking change):

```
ops.two_factor_required               403  guarded action, no X-2FA-Code header. Body carries `action`.
ops.two_factor_invalid_code           401  wrong or expired code. The action did not run; retry is expected.
ops.two_factor_locked                 403  too many failures.
ops.two_factor_enrollment_required    403  restricted session, enrollment not finished (§4).
ops.two_factor_not_enrolled           403  backstop on a guarded action.
ops.two_factor_recovery_not_accepted  403  session authenticated by a recovery code (§3.2).
```

## 9. Merchant portal — login only, this phase

`MerchantIdentity` gets the **enrollment + login half only**. No policy table, no action catalog, no
`X-2FA-Code` anywhere: there is nothing guarded on that side yet.

- New `merchantidentity.MerchantUserTwoFactor` and `MerchantUserRecoveryCode`, identical in shape to §3.1
  and §3.2, plus `MerchantUserSession.TwoFactorMethod`. Migration `AddMerchantUserTwoFactor`.
- **The existing ignored `otp` field is the one that starts working.** `PortalAuthRequests.LoginRequest`
  already carries `Otp` and `MerchantAuthService` discards it — documented as a gap in
  `merchant-portal-frontend-integration.md`. It becomes the code field, so the request shape does not change
  and the frontend contract is additive.
- Forced enrollment exactly as §4, via `MerchantSessionAuthMiddleware`, restricted to
  `/portal/auth/2fa/*` + `/auth/me` + `/auth/logout`, error code `portal.two_factor_enrollment_required`.
  **Corrected (2026-09-25): enrollment happens FIRST, not password change.** `/account/change-password` is
  NOT in that allow-list, so an account still forced through enrollment (§4.1: switch on, not yet bound)
  cannot reach it — the actual order is sign in → enroll 2FA → (if `mustChangePassword`) change password →
  land in the portal. An earlier draft of this doc claimed the opposite; this line replaces that claim.
- Endpoints mirror §8's first four rows under `/api/v1/portal/auth/2fa/*`, plus
  `POST /portal/accounts/{id}/2fa/reset` gated on `portal.accounts.manage`, so a merchant admin can recover
  their own staff without platform involvement.
- **This host DOES emit an `errorCode`** on every failure — an older note in its integration doc claiming
  otherwise was stale, and this work corrected it. The new failures carry `portal_two_factor.*` and
  `portal.two_factor_enrollment_required`, so a SPA can tell "enroll now" from "wrong code" without reading
  display prose.
- The two modules share **no code beyond SharedKernel primitives** (§4.5) — same rule already in force for
  `Pbkdf2PasswordHash` and `OpaqueToken`.

When merchant-side guarded actions are eventually wanted (payout approval is the obvious first), §5's
catalog pattern transplants with `PortalGuardedActions` in the portal host and a per-tenant rather than
platform-wide policy — which is its own T3 design.

## 10. Audit

Every one of these writes an `AuditEntry` through the existing `AuditActor` helper: enrollment started /
confirmed, recovery codes regenerated, admin reset of another account, guarded-action code accepted /
rejected, login 2FA failed, lockout tripped, and every policy change with its before/after guarded set. A
2FA control with no trail cannot answer the only question that matters after an incident: *who supplied the
code on that top-up, and when.*

## 12. Tests that must exist

- RFC 6238 published test vectors, all steps — proves the algorithm rather than asserting it agrees with itself.
- **A refused code mutates nothing**: the guarded handler is never entered, asserted on the underlying
  state, not just the status code. The load-bearing test — a 401 that still performed the action is the
  worst possible outcome here.
- **Retry works**: wrong code → 401, immediately followed by the correct code → 200, same session.
- A code stays valid across several actions inside its step, and is refused two steps later (§6.1).
- **The code never reaches a log**: request-logging redaction covers `X-2FA-Code` and the login body.
- Skew: `-1`, `0`, `+1` accepted; `±2` refused.
- A Pending enrollment satisfies neither login nor a guarded action.
- A recovery code clears login, is refused on a guarded action, and cannot be reused.
- **Forced enrollment**: an unenrolled session reaches the enrollment routes and *nothing else*; confirming
  upgrades it in place.
- **Guarded-action drift guard** (the load-bearing one, modelled on the effective-status test): for every
  code in `GuardedActions.Guardable`, a route exists carrying `.RequireTwoFactor` with that code — so a
  toggle in the settings UI can never be a toggle that guards nothing.
- **The policy action cannot be un-guarded**: save a policy omitting it, read back, still guarded.
- Lockout after N failures, on both login and a guarded action.
- Tenant isolation on the portal side: merchant A cannot reset merchant B's user's 2FA.
- **§4.1's four-scenario truth table**, on both hosts: switch-off skips 2FA at login whether or not a factor
  is bound (and the session's `TwoFactorMethod` stays null even when one is bound); switch-on forces
  enrollment when unbound and demands a code when bound. Plus: an account cannot flip its own switch
  (`cannot_change_own_two_factor_requirement`), another admin can, and a foreign tenant cannot reach a
  portal account's switch at all.
- HTTP on a booted host: 403 `ops.two_factor_required` → same request with `X-2FA-Code` → 200; and a full
  Google Authenticator round trip (scan the real QR, type the real code). Per CLAUDE.md §3, 2FA is not
  "done" until that is observed.

## 13. Deliberately not in this phase

- **Merchant-side guarded actions.** Login only, by decision (§0). §9's last paragraph is the path.
- **WebAuthn / passkeys.** The `code` field is the seam; TOTP first because it needs no hardware rollout.
- **Per-role or per-amount thresholds** ("2FA only above 10,000 USDT"). Real, and deferred: it turns a
  string match into a rule engine, and platform-wide is what was asked for.
- **Trusted devices / "remember this browser".** A convenience that materially weakens login 2FA.
- **Single-use codes.** Rejected deliberately (§6.1); revisit only if the ~90-second reuse window is ever
  judged to matter more than being able to work through a queue.
- **Revoking live sessions on a 2FA reset.** Matches the existing gap for a disabled account (refused at
  next login, not proactively killed) — worth fixing for both at once, not here.
